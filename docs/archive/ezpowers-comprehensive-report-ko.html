4. 명령어 9종 상세

/setup — 하네스 초기화명령어

프로젝트 설정, 스티어링 문서, 페이즈 추적 인프라를 생성합니다. --enable-traces로 트레이스 수집 활성화, --with-evals로 eval 디렉터리 초기화.

/brainstorm — 설계 세션명령어

대화형 설계 → Spec 문서 생성. HARD-GATE: spec 승인 전 구현 금지. 요구사항별 Input/Behavior/Output/Impact scope/AC/Edge cases 6개 필수 필드. Given/When/Then/Verify/Verify-type 구조. 22개 금지 모호 표현 자동 탐지.

/plan — 태스크 분해명령어

Spec을 실행 가능한 태스크로 분해. Coverage Matrix(모든 R이 ≥1개 T에 매핑 필수), Impact scope(참조 깨짐 + 방어 코드 보존), 의존성 그래프, TDD 체크리스트. plan-reviewer 에이전트가 6개 Hard Gate 검증.

/choiceexecutor — 실행 라우터명령어

3가지 실행 경로: (1) 서브에이전트 (4+ 태스크), (2) 하네스 위임, (3) 인라인. 태스크별 AC 검증, 조건부 보안 리뷰(27개 키워드), 최종 코드 리뷰, 진동 감지, 세션 재개 지원.

/executeharness — 하네스 위임명령어

Plan → Phase 변환 (Task N → step{N-1}.md), EasyPowersHarness Python executor에 위임, index.json 백업/복원 메커니즘.

독립 유틸리티: /review, /sync-docs, /eval, /feedback명령어

/review: Spec 대비 구현 완전성 검증 (5개 체크리스트). /sync-docs: 참조 문서와 코드베이스 동기화. /eval: eval 스위트 실행 + 버전별 점수 보고. /feedback: 세션 트레이스에 +1/-1 점수 부착.

7. TicketSSOT 프로젝트 개요

TicketSSOT란? AI 네이티브 티켓 기반 개발 방법론의 연구 및 문서 허브입니다. 실제 코드베이스가 아니라, Arcanaverse TRPG 엔진 백엔드를 위한 거버넌스, 아키텍처, 프로세스 문서 체계입니다.

8. TicketSSOT 핵심 방법론

8.1 티켓 기반 개발 (Ticket-Driven Development)

티켓 생성 (docs/tickets/) ↓ AI 에이전트가 정해진 순서로 문서 읽기 (SSOT → ARCH → RULES → GUIDE) ↓ 구현 전 분석 (root cause, 수정 파일 목록, 구현 계획) ↓ 승인 대기 (코딩 전 사람 확인) ↓ 최소 범위 구현 (API → Usecase → Adapter 패턴) ↓ QA 실행 (검증 단계 수행) ↓ 리포트 작성 (docs/analysis/) ↓ 배포 + Oracle VM 검증 ↓ 최종 완료 (Release Verified: YES, Ticket Done: YES)

8.2 완료 정의 (Definition of Done) 6단계

단계내용주체
1. 기능 완료모든 AC 충족, 의도된 동작 일치, 기능 누락 없음AI
2. 범위 준수허용된 파일만 수정, 부작용 없음, 무관한 리팩토링 없음AI
3. 리포트 완료docs/analysis/에 리포트 존재, 네이밍 규칙 준수AI
4. QA 검증모든 검증 단계 실행, 핵심 플로우 정상, 회귀 없음AI
5. 릴리스 검증CI/CD 배포, Oracle VM에서 실제 브라우저 검증사람
6. 최종 승인사람이 최종 확인, 머지 결정사람

8.3 AI 에이전트 규칙 16가지 (핵심 발췌)

  • 진실의 원천 우선순위: SSOT.md > PRD > GitHub Issue
  • 이슈 기반: 1 Issue = 1 Branch = 1 PR (절대 병합 금지)
  • 최소 변경: 영향받는 파일만 수정, 기존 패턴 재사용
  • 아키텍처 경계 존중: API/Domain/Usecase/Adapter/Infra 레이어 준수
  • 금지 항목: DB 스키마 변경, 인프라 변경, 환경변수 수정 (명시적 요청 제외)
  • 안전 규칙: 아키텍처/DB/인프라 변경에 확신이 없으면 즉시 멈추고 확인 요청

9. TicketSSOT 거버넌스 체계

문서 계층 구조와 갈등 해결

SSOT.md (최상위 권한 — 모든 갈등에서 우선) ↓ ARCHITECTURE.md (시스템 아키텍처) ↓ AI_AGENT_RULES.md (에이전트 행동 규칙) ↓ DEVELOPMENT_GUIDE.md (개발 워크플로우) ↓ 개별 티켓 (docs/tickets/TYPE-ID_description.md)

문서 구조 잠금 (Documentation Structure Lock)

허용 (일반 작업 시):
- docs/tickets/ 생성/수정
- docs/analysis/ 생성/수정
- docs/scratch/ 임시 메모
금지 (일반 작업 시):
- 새 문서 시스템/폴더 도입
- docs 폴더 구조 변경
- 핵심 아키텍처 문서 이동

10. TicketSSOT → EZPowers 패턴 매핑

핵심 발견: 코드 복사가 아니라 아키텍처 패턴의 영향입니다. TicketSSOT의 AI 거버넌스 개발 방법론이 EZPowers에서 Claude Code 플러그인이라는 다른 도메인에 맞게 재구현되었습니다.

10.1 SSOT 거버넌스 → 다층 권한 문서 체계

TicketSSOT원본
  • SSOT.md 단일 최상위 권한
  • "갈등 시 SSOT 우선" 원칙
  • 문서 구조 잠금
  • 정해진 읽기 순서 (7단계)
EZPowers적용
  • CLAUDE.md + AGENTS.md + docs/INDEX.md 3층 구조
  • authority 마커: [canonical] / [supporting] / [derived]
  • /sync-docs에서 Conventions/Boundaries 보호
  • /setup이 자동 생성 → 수동 생성 제거
기대효과: 프로젝트 컨텍스트가 자동으로 모든 단계에 주입되어, 에이전트가 프로젝트를 처음 보더라도 일관된 행동을 보장합니다. TicketSSOT의 수동 읽기 순서를 자동화한 것.

10.2 티켓 템플릿 → Spec 구조화 (R1~Rn)

TicketSSOT 티켓원본
  • Problem / Context / Scope / Strategy / AC / Verification
  • 번호 매긴 Acceptance Criteria (1, 2, 3...)
  • 수동 검증 단계 (Start API, Open..., Inspect...)
  • 1 Ticket = 1 Report 매핑
EZPowers Spec적용
  • Input / Behavior / Output / Impact scope / AC / Edge cases (6개 필수 필드)
  • R1, R2... 고유 ID 부여 + Given/When/Then/Verify/Verify-type
  • 자동 실행 가능한 Verify 커맨드 (exit 0 = PASS)
  • Coverage Matrix로 R ↔ T 추적성 보장
기대효과: TicketSSOT의 "수동 검증 단계"가 기계적으로 실행 가능한 셸 커맨드로 진화. 사람이 브라우저를 열지 않아도 AC 통과 여부를 자동 판정할 수 있습니다.

10.3 AI 에이전트 규칙 → Hard Gate 시스템

TicketSSOT원본
  • 16개 규칙 문서 (AI_AGENT_RULES.md)
  • "불확실하면 멈추고 확인" 안전 규칙
  • 범위 준수 체크리스트 (DoD 2.2)
  • 구현 전 승인 대기
  • 시행: 에이전트 양심에 의존 (문서 기반)
EZPowers적용
  • <HARD-GATE> 마커로 통과 불가 게이트 설정
  • 진동 감지 (같은 이슈 3회 반복 → 사용자 에스컬레이션)
  • implementer-prompt의 Scope Guard (Files 섹션만 수정)
  • 설계 → 승인 → 플랜 순서 강제
  • 시행: 기계적 강제 (pre-commit 훅 + 리뷰어 서브에이전트)
기대효과: TicketSSOT에서 "에이전트 양심"에 의존하던 규칙 준수가 기계적 강제로 업그레이드. 규칙을 "읽었지만 무시하는" 문제를 원천 차단합니다.

10.4 DoD 6단계 → 다층 검증 체계

TicketSSOT DoD원본
  1. 기능 완료
  2. 범위 준수
  3. 리포트 완료

13. 종합 기대효과 분석

13.1 TicketSSOT 패턴 적용으로 얻는 효과

효과 1: 설계-구현 단절 제거프로세스

TicketSSOT 문제: 티켓의 AC가 자유 형식이라 구현자가 해석에 따라 다르게 구현할 수 있음.

EZPowers 해결: Given/When/Then/Verify 구조로 AC를 기계 실행 가능하게 만들고, Coverage Matrix로 모든 요구사항이 태스크에 매핑됨을 증명.

기대효과: "구현했는데 요구사항이 빠져있었다"는 문제가 구조적으로 불가능해짐. 요구사항 누락률 0%에 근접.

효과 2: 검증 자동화로 피드백 루프 단축속도

TicketSSOT 문제: Oracle VM에서 사람이 브라우저로 확인해야 완료. 배포-검증 사이클이 최소 수십 분.

EZPowers 해결: Verify 커맨드가 exit 0으로 즉시 판정. AC 검증이 초 단위로 완료.

기대효과: 피드백 루프가 "분" 단위에서 "초" 단위로 단축. 하루에 처리할 수 있는 태스크 수가 3~5배 증가.

효과 3: 규칙 준수의 기계적 강제품질

TicketSSOT 문제: AI 에이전트 규칙 16가지가 문서로만 존재. 에이전트가 규칙을 읽고도 무시할 수 있음.

EZPowers 해결: HARD-GATE, pre-commit 7체크, 리뷰어 서브에이전트가 규칙 위반을 커밋 전에 차단.

기대효과: "규칙은 있지만 지켜지지 않는" 문제 해결. 규칙 준수율이 문서 기반 ~70%에서 게이트 기반 ~99%로 상승.

효과 4: 측정 기반 지속적 개선진화

TicketSSOT 문제: 프로세스 효과를 정량적으로 측정할 방법이 없음. "잘 되고 있다"는 느낌에 의존.

EZPowers 해결: Eval 3-way split(golden/optimization/holdout) + 베이스라인 비교 + hill-climbing 자동 최적화.

기대효과: 매 변경의 효과를 숫자로 증명. 회귀 자동 차단(golden 100%), 과적합 방지(holdout ≤5% 하락), 지속적 개선(optimization Δ≥0).

효과 5: 프로젝트 컨텍스트 자동 주입효율

TicketSSOT 문제: AI가 SSOT → ARCH → RULES → GUIDE 순서로 7개 문서를 읽어야 컨텍스트 파악. 읽기 순서를 어기면 잘못된 가정.

EZPowers 해결: /setup이 AGENTS.md, INDEX.md를 자동 생성하고, 각 명령어가 필요한 컨텍스트를 자동으로 로드.

기대효과: "문서를 안 읽어서 잘못 구현"하는 문제 원천 차단. 에이전트 온보딩 시간이 0에 근접.

효과 6: 영향 범위 정밀 추적안전

TicketSSOT 문제: "Scope" 섹션에서 허용/금지를 텍스트로만 기술. 실제로 관련 파일을 누락하기 쉬움.

EZPowers 해결: Impact scope를 3단계로 분류: (a) 참조 깨짐(grep으로 실제 import 교차 검증 + 1-hop re-export), (b) 호출 사이트 정보, (c) 방어 코드 보존.

기대효과: "수정했더니 다른 곳이 깨졌다"는 회귀 버그가 plan 단계에서 사전 발견. 구현 후 디버깅 시간 대폭 감소.

15. 결론 및 로드맵

TicketSSOT → EZPowers: 패턴 진화의 의미

TicketSSOT은 "AI와 사람이 함께 개발하는 거버넌스 체계"를 문서로 정립했습니다. EZPowers는 이 거버넌스를 기계적으로 강제하는 플러그인으로 구현했습니다.

TicketSSOT의 "사람이 읽고 따르는 규칙" ↓ 패턴 추출 & 자동화 EZPowers의 "기계가 강제하는 게이트" 핵심 전환: 문서 기반 거버넌스 → 게이트 기반 거버넌스 수동 검증 (Oracle VM) → 자동 검증 (Verify exit 0) 느낌 기반 품질 → 측정 기반 품질 (eval 3-way split) 일회성 구현 → 지속적 최적화 (hill-climbing)

종합 기대효과 한 줄 요약

TicketSSOT의 연구가 EZPowers에 적용됨으로써,
"AI가 규칙을 읽고 따르기를 바라는" 방식에서
"AI가 규칙을 어기면 커밋이 차단되는" 방식으로 진화했습니다.
