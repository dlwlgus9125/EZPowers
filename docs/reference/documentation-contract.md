# Documentation Bootstrap Contract

This contract defines the repository-aware documentation bootstrap, including
the DESIGN.md profile lane added in EZPowers 5.5. Setup may analyze a project
and stage structured Markdown, but
only the project-local runtime may validate ownership, preview exact changes,
apply a confirmed bundle, register the graph, and enforce documentation lint.

The design generalizes two useful patterns without importing their
orchestration policy: OMC's hierarchical repository guidance and OMX's
root-level `AGENTS.md` setup. EZPowers adds explicit evidence, whole-file
ownership, conflict-safe adoption, and a deterministic local lint gate.

## Authority And Required Roots

Every ready documentation graph contains:

- `AGENTS.md`: the canonical repository instruction document;
- `CLAUDE.md`: exactly `@AGENTS.md`, so Claude reads the same authority;
- `docs/INDEX.md`: the human and agent navigation root.

`AGENTS.md` is authority `canonical`. Other documents are `supporting` or
`derived` unless the repository already establishes a narrower canonical
source. Nested `AGENTS.md` files are optional and should be created only where
a subtree has genuinely distinct working or verification rules.

Existing user-authored documents remain authoritative evidence. Setup must not
copy them into generated prose, silently claim ownership, or create competing
sources. A registered `external` document is checked for existence and may be
linked by the graph, but its bytes are never owned by EZPowers.

## Repository Analysis

Inspect before drafting:

- repository instructions and existing Markdown;
- source roots, package/workspace manifests, dependency locks, and build files;
- CI workflows, test configuration, scripts, and deploy or operations files;
- `.ezpowers/config.json`, existing specs/plans, and product documents;
- existing root or frontend-local `DESIGN.md` files and their implementation
  roots, without automatically adopting them;
- meaningful module or service boundaries.

Ignore generated, vendored, cache, dependency, build-output, evidence, staging,
backup, and local-wiki trees. Never infer a command, architecture boundary,
ownership rule, dependency, or product claim from a directory name alone.
Every generated document entry has a non-empty `evidence` array containing
safe repository paths or an explicit `user:<decision>` or `default:<policy>`
reference.

When evidence is missing, stage an `incomplete` bundle or omit the optional
document. Do not emit TODO markers or plausible-sounding filler.

## Adaptive Document Set

Create the smallest useful graph. In addition to the three required roots,
select documents only when repository evidence supports them:

| Repository signal | Suggested document |
| --- | --- |
| multiple modules, services, packages, or runtime boundaries | the project's architecture reference |
| stable language, naming, formatting, or contribution rules | a focused contributor convention guide |
| unit/integration/e2e tooling or non-obvious test commands | a focused testing guide |
| deployment, migration, incident, release, or operator workflows | an operations runbook |
| public API, protocol, schema, or compatibility surface | a focused reference document |
| a maintained frontend or independently branded UI root | paired `docs/ux/frontend-design.md` and nearest `DESIGN.md` artifacts |
| settled durable tradeoff | a numbered ADR under `docs/decisions/` |

Do not create generic README mirrors, one document per directory, or duplicate
spec and plan prose. Existing `docs/specs/` and `docs/plans/` remain owned by
their narrow workflow skills and are indexed rather than regenerated by setup.

## Generated Markdown

Except for the exact `CLAUDE.md` import shim and profile-validated `DESIGN.md`,
each EZPowers-owned Markdown file starts with flat YAML frontmatter:

```yaml
---
doc_type: "reference"
authority: "supporting"
status: "active"
generated_by: "ezpowers"
---
```

It contains one H1 and a `## Evidence` section that identifies the repository
sources behind its claims. Frontmatter authority is `canonical`, `supporting`,
or `derived`; status is `draft` or `active`. Generated files use UTF-8 and are
managed as whole files. Manual edits to a managed file are drift, not a merge
input.

## Staged Bundle

Setup writes proposed files only below
`.ezpowers/staging/<unique-bundle>/` and a `bundle.json` with schema version 1:

```json
{
  "schema_version": 1,
  "status": "ready",
  "replace_links": true,
  "documents": [
    {
      "path": "AGENTS.md",
      "source": "files/AGENTS.md",
      "role": "repository-instructions",
      "ownership": "ezpowers",
      "authority": "canonical",
      "status": "active",
      "validator": "markdown",
      "evidence": ["package.json", "user:working agreements"],
      "adopt": false
    }
  ],
  "links": [
    {"from": "CLAUDE.md", "to": "AGENTS.md", "relation": "imports"}
  ]
}
```

Paths are project-relative. Document targets are limited to `AGENTS.md`,
`CLAUDE.md`, Markdown under `docs/`, and exact `DESIGN.md` names at safe root or
application paths. Runtime, host metadata, dependency, cache, and build-output
directories are forbidden DESIGN.md targets. Sources remain inside the
selected bundle. Roles use safe IDs. Ownership is `ezpowers` or `external`;
validators are `markdown`, `spec`, `plan`, or `design-md`; graph relations are
`imports`, `indexes`, `parent`, or `references`.

A `design-md` entry must include a safe `validator_profile`, for example:

```json
{
  "path": "DESIGN.md",
  "source": "files/DESIGN.md",
  "role": "design-system",
  "ownership": "ezpowers",
  "authority": "canonical",
  "status": "active",
  "validator": "design-md",
  "validator_profile": "google-alpha-0.4.0-ezpowers-1",
  "evidence": ["docs/ux/frontend-design.md", "src/app.css"]
}
```

An external entry has no staged source and must already exist. Set `adopt:
true` only when the user explicitly chooses to replace an existing unmanaged
target with the staged whole-file version.

## Preview, Apply, And Refresh

Run:

```text
python .ezpowers/ezpowers.py docs preview --bundle .ezpowers/staging/<bundle> --json
python .ezpowers/ezpowers.py docs apply --bundle .ezpowers/staging/<bundle> --preview-sha256 <sha> --json
python .ezpowers/ezpowers.py docs lint --json
python .ezpowers/ezpowers.py docs status --json
```

Preview validates sources, metadata, evidence, graph entries, current target
hashes, config, and the current registry. Its SHA-256 binds the complete
proposal and the observed target/config state. Apply rejects a stale preview.
For DESIGN.md updates the preview also includes token additions, removals and
modifications, section changes, diagnostic deltas, and regression reasons.

Ordinary apply creates missing files and updates unchanged managed files. It
preserves unmanaged files, missing/edited managed files, and explicit
adoptions as conflicts. `--force` is valid only after the user accepts the
reported conflict list. It backs up each replaced target below
`.ezpowers/backups/docs/<timestamp-id>/` before writing. Unmanaged files still
require `adopt: true`; force alone never claims them.

Successful apply updates `.ezpowers/docs.json` and removes the applied staging
bundle. If status is `ready`, it registers `ezpowers.docs` as an exact required
`static` check in `.ezpowers/config.json`. A graph containing `design-md`
entries must have exactly one `frontend-design` role and also registers the
exact `ezpowers.design` `check-project` command. Apply runs lint before
committing the transaction. Any failure restores the previous documents,
registry, and config.

`setup --refresh` repairs the installed kit only. Documentation analysis and
replacement are always a separate, explicit setup `--refresh-docs` workflow
that stages a new bundle, presents its preview, and applies only after
confirmation.

## Registry And Lint

`.ezpowers/docs.json` records graph status, document role, ownership,
authority, validator, optional DESIGN.md profile, evidence, managed SHA-256,
links, and update time. It is
project data and participates in completion freshness. It also binds the exact
interpreter and argv of the required `ezpowers.docs` check so invoking lint
through another compatible Python installation does not redefine the
registered command.

`docs lint` fails when:

- a required root, registered target, evidence source, or graph endpoint is
  missing or unsafe;
- a managed file differs from its registered hash;
- generated metadata, title, Evidence section, spec/plan block, or exact
  `CLAUDE.md` import is invalid;
- a registered DESIGN.md fails its retained profile, its frontend mapping is
  missing or ambiguous, or the nearest mapping does not own an implementation
  path;
- a Markdown link, declared import, parent marker, index link, or reference is
  unresolved;
- the required `ezpowers.docs` check is absent or changed.
- `ezpowers.design` is absent or changed when the graph contains DESIGN.md.

An older registered profile remains valid. Moving a document to a newer
profile is an explicit staged update subject to the same preview, adoption,
force, and backup rules; refresh never rewrites the profile in place.

The local `.ezpowers/staging/`, `.ezpowers/backups/`, and `.ezpowers/wiki/`
trees are excluded from completion fingerprints. Applied documentation, the
registry, and config are not excluded.
