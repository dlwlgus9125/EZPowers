1. Project Identity & Philosophy

EZPowers is a personal Claude Code skill plugin implementing Spec-Driven Development (SDD): humans design and review, agents implement.

Design before codeHARD-GATE: no implementation before spec approval
Evidence-based verification"should work" banned; exit-code proof required
Assumptions declaredExplicit ASSUMPTIONS block before design proposals
YAGNIBuild only what's needed now
One question at a time/brainstorm asks single questions, never overwhelming
No skill chainingEach skill independently callable; eval-diagnostician is sole exception

6. /brainstorm — Design Session

/brainstorm command

Purpose: Transform user ideas into formal spec documents through structured, conversational design. No code is written.

HARD-GATE: No implementation before user-approved spec. Even "trivially simple" projects require design → approval → plan.

Conversational Flow

1. Read project context (AGENTS.md, config.json, git history, docs/) 2. Set phases/index.json brainstorm = "in_progress" 3. Ask ONE question at a time (domain questions BEFORE implementation questions) - Scope → Constraints → Success criteria - Prefer multiple-choice; open questions OK - Skip already-known info 4. Present 2-3 approaches with trade-offs + recommendation 5. Section-by-section design presentation with user approval at each step 6. Declare ASSUMPTIONS explicitly; user corrects if wrong 7. Extract Requirements (R1, R2, ...) - user confirms completeness - If 10+ requirements → propose sub-project decomposition - If 3 consecutive missing requirements → return to question phase 8. Write spec document + verify.sh + INDEX.md update + git commit 9. Spec Review Loop (ezpowers:spec-reviewer subagent) - PASS/FAIL verdict parsing; oscillation detection; max 5 iterations 10. User final review → approval → phases/index.json complete + artifact path

Spec Document Structure (per Requirement)

SectionContentRequired?
InputTrigger or input (or "Before state" for deletion)HARD GATE
BehaviorStep-by-step actions (not single sentence)HARD GATE
OutputObservable result (or "After state" for deletion)HARD GATE
Impact scopeAffected modules/componentsHARD GATE
Acceptance criteriaGiven/When/Then/Verify/Verify-typeHARD GATE
Edge casesBoundary conditions + expected behaviorHARD GATE

Verify-type Classification

TypeWhenTimeoutExample
apiREST/GraphQL endpoint30scurl -s localhost:3000/api/users | jq '.status'
e2eUser-facing UI flow120splaywright test login.spec.ts
cliCLI command behavior30smycli --version
libLibrary function via inline script30snode -e "assert(parse('k=v').k === 'v')"
dataData migration, schema, ETL60sSELECT count(*) FROM users
purePure function, no side effects30sassertEquals(add(1,2), 3)

Banned Vague Expressions (Auto-FAIL if present)

Korean (14): 적절히, 적절하게, 필요한 경우, 필요 시, 등등, 기타, 올바르게, 정상적으로, 효율적으로, 최적화하여, 가능하면, 가급적, 상황에 맞게, 상황에 따라
English (8): appropriately, if necessary/needed, etc./and so on, properly/correctly, efficiently/optimized, if possible/preferably, as appropriate, depending on

7. /plan — Task Decomposition

/plan command

Purpose: Decompose spec into executable tasks with agent assignments, dependency graph, and Coverage Matrix.

Process (9 Steps)

1. Pre-flight: Verify config.json, AGENTS.md, locate spec document 2. Read spec + declare assumptions (user confirms) 3. Scope check: if multiple independent subsystems → split into separate plans 4. File structure mapping (before task definition) 5. Coverage Matrix (HARD GATE): Every R must map to ≥1 Task 6. Structural Invariants table (from AGENTS.md/CLAUDE.md rules) 7. Task decomposition with full structure 8. Agent assignment (isolated/sequential/parallel modes) 9. Plan Review Loop (ezpowers:plan-reviewer subagent) - 6 hard-gate checks; oscillation detection; max 5 iterations

Task Structure Template

### Task N: [Name] [R1, R3]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

**Impact scope:**
- (a) Reference breakage: [direct importers + 1-hop re-exports]
- (b) Call site info: [behavioral dependency only, reference]
- (c) Code preservation: [defensive code that must survive]

**Depends on:** Task N (explicit prerequisite)
**File overlap with:** Task N (same file modified)

**Completion criteria:** (verbatim from spec)
- [ ] (R1) Given: ... / When: ... / Then: ... / Verify: `cmd` / Verify-type: lib

**Verification method:** `command` (exit 0 = PASS)
**Runtime verification:** `start-cmd & sleep N && kill $!` pattern

Steps: Write test → Verify fail → Implement → Verify pass → Commit

Plan Review Hard Gates (ANY failure = FAIL)

#CheckWhat It Validates
1Coverage MatrixEvery R from spec present; every R maps to ≥1 T
2Task Completion CriteriaEvery task has criteria tagged with R numbers
3Verification MethodsEvery task has specific command (not vague)
4Impact Scope(A) Section exists, (B) reference breakage cross-verified via grep, (C) defensive code preserved
5Test-Given AlignmentTest setup matches GWT abstraction level; assertions verify Then
6Build ConfigIf build config modified: CJS/ESM compatibility validated

8. /choiceexecutor — Execution Router

/choiceexecutor command

Purpose: Execute plan tasks via one of 3 paths, with dependency graph analysis, AC verification, security review, and final code review.

Three Execution Paths

PathNameWhenHow
1Subagent-driven (Recommended)4+ tasksFresh agent per task via implementer-prompt template; context isolation
2Harness executionharness.root configured + step logging neededDelegates to /executeharness; Python executor with phase files
3Inline execution1-3 independent tasksCurrent session sequential; context budget check (>40% warns)

Per-Task Execution Loop (Subagent Path)

1. Git hash recording (task-start-hash; first-task-start-hash for final review) 2. Task complexity assessment (scope, coupling, context breadth) 3. Dispatch implementer subagent (template placeholder substitution) 4. Handle status: DONE / DONE_WITH_CONCERNS / BLOCKED / NEEDS_CONTEXT 5. AC Verification: Run Verify commands (exit 0 = PASS) - Server management for api/e2e types (start, health check, stop) - FAIL → re-dispatch max 3 times; then user escalation 6. Conditional Security Review: If 27 security keywords detected - Dispatch ezpowers:security-reviewer subagent 7. Calculate changed files (git diff + untracked) 8. Next task

Review Loop Protocol

Review TypeMax IterationsWarn AtOscillation Detection
Implementer AC3--
Security Review53Same {file}:{issue_type} key in 2+ prior iterations
Final Code Review105Same key in 2+ prior iterations → user escalation

Session Resumption

If build phase is in_progress with checked tasks, user gets 4 options:

  • Resume — Skip completed, continue from incomplete
  • Re-run current — Reset only incomplete task's checkbox
  • Full re-run — Reset all checkboxes, restart everything
  • Stop — Maintain current state

Completion Sequence

1. Final Code Review (all paths converge): diff first-task-start-hash..HEAD 2. Offer /sync-docs (reference documentation sync) 3. Run smoke test if config.smoke.command is non-empty 4. Recommend /review 5. Update phases/index.json: build = "complete"

9. /executeharness — Harness Delegation

/executeharness command

Purpose: Thin wrapper that converts EZPowers plan to EasyPowersHarness phase format, delegates step-by-step execution to Python executor, and restores EZPowers state afterward.

Plan-to-Phase Conversion

EZPowers PlanHarness PhaseRule
Plan header (Goal, Arch, Tech)phase-context.mdVerbatim copy
Task Nstep{N-1}.md0-indexed (Task 1 → step0)
Task listindex.jsonHarness schema with step status tracking

Index Protection (Schema Conflict Resolution)

Before: cp phases/index.json → phases/index.ezpowers.json (backup) During: Harness executor uses phases/index.json freely After: Restore phases/index.json from backup; delete backup Update build phase status based on results

Step Execution Loop

for each pending step:
  python "{harness_root}/scripts/execute.py" {feature-name}  # 600s timeout
  Read phases/{feature-name}/index.json for step status
  completed → PASS | error → FAIL | blocked → BLOCKED
  FAIL/BLOCKED → escalate to user + stop loop

10. /review — Change Review

/review command

Independent review against spec. Runs verify commands, checks architecture adherence, test existence, security, and build.

5 Checklists

  • 3-1: Spec compliance (all R's AC reflected, Verify commands pass, Impact scope matches diff)
  • 3-2: Architecture adherence (directory structure, layer boundaries, wiring)
  • 3-3: Test existence (corresponding tests, mock usage balance)
  • 3-4: Security (input validation, auth, injection, credential exposure)
  • 3-5: Build/Test (config.build.command, config.test.command, config.lint.command)

Output: [path:line] [severity] description (critical > major > minor)

14. Plugin Agents

spec-reviewer agent · sonnet

Validates spec document completeness. Dispatched by /brainstorm after spec creation.

8 Hard Gate Checks

  1. Requirements coverage (all R's have sections)
  2. Structural completeness per R (6 mandatory fields)
  3. Banned expression scan (14 Korean + 8 English)
  4. Impact scope cross-verification (grep codebase imports + 1-hop re-exports)
  5. Given-When-Then structure (Given/When/Then/Verify/Verify-type fields)
  6. Implementation term detection (no camelCase/snake_case in GWT text)
  7. Verify command validation (valid shell syntax + valid type)
  8. Technology constraint resolution (ESM/native/platform-specific strategies)
plan-reviewer agent · sonnet

Validates plan executability. Dispatched by /plan after plan creation.

6 Hard Gate Checks

  1. Coverage Matrix (all Rs mapped to ≥1 T)
  2. Task completion criteria (tagged with R numbers)
  3. Verification methods (specific commands, not vague)
  4. Impact scope (existence + reference breakage + code preservation)
  5. Test-Given alignment (setup ↔ Given, assertion ↔ Then)
  6. Build config cross-validation (CJS/ESM compatibility)
code-reviewer agent · inherit

Final code quality gate. Generates Spec Evidence table mapping R's to file:line locations. Read-only (no Write/Edit tools).

Review Dimensions

Plan alignment, error handling, type safety, SOLID principles, package integrity (typosquat detection), module system compatibility, Spec Evidence table (VERIFIED/MISSING), Structural Invariants execution.

security-reviewer agent · inherit

Scans for OWASP Top 10 + AI-specific vulnerabilities. Read-only. Triggered by 27 security keywords.

AI-Specific Patterns

Missing input sanitization, hallucinated API parameters, overly permissive defaults (open CORS), deprecated crypto (MD5/SHA1), hardcoded credentials, string concatenation in queries.

implementer-prompt template

Template for task subagents. /choiceexecutor substitutes 8 placeholders before dispatch.

Key Constraints

  • Scope guard: only modify files in plan's Files section
  • Command safety: forbidden to call parent commands
  • Context anchoring: read AGENTS.md + git log + related files before writing
  • Test impact analysis: run tests before AND after implementation
  • 3+ fix failures: suspect architecture, escalate as BLOCKED
  • Status: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
eval-diagnostician agent · opus

Analyzes failing eval traces, proposes ONE 1-3 line change. Only agent not user-facing (called from scripts only).

Process

Cluster failures by root cause → identify largest cluster → read command file → find minimal change → predict which case IDs flip. Output: strict JSON schema with anti-overfitting rules (≥2 cases must improve).

15. Independent Skills

diagnose skill · 6-Phase

Iron Law: "NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST"

PhaseFocusKey Technique
1. Root Cause InvestigationEvidence collection, data flow tracingBackward call stack tracing (root-cause-tracing.md)
2. Pattern AnalysisFind working similar code, list ALL differencesReference implementation comparison
3. Hypothesis & TestingSingle hypothesis, minimal change, one variableScientific validation loop
4. ImplementationTest BEFORE fix, single fix, validateDefense-in-depth (4-layer validation)
3+ Fix Failure Rule: After 3 failed fixes, suspect architecture. STOP and discuss with user. Do not attempt Fix #4.
verifyself skill · CoVe 6D

Chain-of-Verification: converts "did I think deeply enough?" into "is this fact correct?"

#DimensionWhat It Checks
1Exploration DepthAssumptions vs verified facts
2Impact ScopeAll affected areas considered?
3Alternative ConsiderationWere alternatives explored?
4Temporal PerspectiveSustainable over time?
5Context AlignmentFollows project norms?
6Evidence SufficiencyClaims verifiable and traceable?

Verdicts per dimension: PASS / CONCERN / FAIL. Any FAIL/CONCERN triggers proposal revision.

writing-skills skill · TDD Meta

TDD-based skill authoring: RED (observe failure without skill) → GREEN (write minimal skill) → REFACTOR (close loopholes).

Pressure Testing

7 pressure types: Time, Sunk cost, Authority, Economic, Fatigue, Social, Pragmatic. Good scenarios combine 3+ pressures and force concrete action choices.

Three-Layer Architecture

1. Plugin Hookshooks/hooks.jsonClaude Code fires events at SessionStart, PostToolUse(Edit/Write/Read), Stop, SessionEnd
2. Trace Collectionbin/trace.shOTel-compatible JSONL writer; observation-only; always exits 0

Trace JSONL Format (OTel GenAI Semantic Conventions)

{
  "trace_id": "8c1e...",        "span_id": "a4b2...",
  "session_id": "abc123",       "hook_event_name": "PostToolUse",
  "tool_name": "Edit",          "tool_input": {...},
  "gen_ai.system": "anthropic", "gen_ai.request.model": "claude-opus-4-5",

Observation-Only Constraint: Hooks must NEVER modify model behavior. Forbidden: changing tool inputs/outputs, blocking execution, injecting instructions. Allowed: append-only JSONL writing, metadata extraction.
