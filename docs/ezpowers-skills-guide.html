어떤 스킬을,
언제 써야 할까?

모든 작업에 모든 스킬을 쓰는 것은 아닙니다. 요청의 모호함, UI 결정, 기술 경계, 검증 방식에 따라 필요한 경로만 골라 쓰고, 마지막 완료 판단은 실제 프로젝트 검사와 신선한 증거로 내립니다.

01 · Invocation

호스트와 설치 위치에 따라
호출문이 달라집니다

개념과 완료 판정은 같지만 Claude Code와 Codex의 네임스페이스는 다릅니다. 아래 호스트를 바꾸면 이 페이지의 모든 명령 예시가 함께 바뀝니다.

사용 중인 호스트

선택은 이 브라우저에만 저장되며 프로젝트를 변경하지 않습니다.

플러그인 스킬 설치된 EZPowers 플러그인
$ezpowers:spec
프로젝트 스킬 setup 후 저장소 로컬 복사본
$spec
hud는 전역 Codex 상태 표시줄을 관리하는 플러그인 전용 스킬이라 프로젝트 키트에 설치되지 않습니다. 나머지 12개 스킬은 setup 후 프로젝트 로컬 호출이 가능합니다.
플러그인: 13개

네임스페이스를 붙여 호출합니다. setup 전에도 배포본의 스킬을 사용할 수 있습니다.

프로젝트 키트: 12개

저장소 안에 자체 포함되며 원본 플러그인 체크아웃 없이도 두 호스트에서 동작합니다.

완료 판정: 동일한 코어

호스트 어댑터는 다르지만 검증, 증거 해시, 신선도, 인증 규칙은 프로젝트 로컬 런타임이 판단합니다.

02 · Main route

기본 작업 흐름은
하나의 얇은 경로입니다

노란 마름모는 조건부 판단입니다. 해당 문제가 없으면 건너뜁니다. 확인·설계 단계가 끝나면 같은 주 경로로 돌아옵니다.

Evidence discipline

diagnose

exact-red와 최소화를 먼저 증명한 뒤에만 가설을 쓰며, 재현할 수 없으면 추측 수정 없이 필요한 증거를 요청합니다.

Focused design

codebase-design

지정된 모듈에서 최소 두 인터페이스와 실제 seam을 비교하며, 저장소 전체를 스캔하지 않습니다.

Explicit review

improve-codebase-architecture

명시 호출 시 제품 코드를 넓게 살펴 임시 오프라인 보고서를 만들고, 선택한 후보 하나만 더 탐색합니다.

Supporting memory

wiki

어느 단계에서든 로컬 지식을 찾고 보조할 수 있지만, 저장소 근거와 완료 증거를 대체하지 않습니다.

Explicit route

harness-chain

명시적으로 구성·승인했을 때만 한 기능을 제한된 무인 루프로 진행하는 별도 경로입니다.

Global utility

hud

프로젝트 흐름과 무관하게 전역 Codex 모델·사용량 상태 표시줄만 관리합니다.

01

setup

설치 · 복구 · 문서 기반
↗
명시 호출 plugin + project

저장소에 자체 포함형 EZPowers 키트를 설치·갱신·복구하고, 실제 프로젝트 검사와 선택적 문서 그래프를 구성합니다.

언제
최초 설치, 버전 갱신, 설치 손상 복구, 문서 부트스트랩/재분석
결과
.ezpowers/, 호스트별 로컬 스킬, 검사 설정, 선택적 문서 그래프
안 함
제품 코드 작성, 모델 선택, 전역 HUD 구성, 외부 실행기 추가
Plugin invocation권장 첫 호출
$ezpowers:setup
실행 흐름과 주의점
  1. 저장소 근거에서 Python 3.10+, 실제 검사 명령, 문서 권한을 확인합니다.
  2. 새 설치 또는 --refresh로 키트를 복사하고 충돌을 보존합니다.
  3. 문서는 스테이징 → 해시 미리보기 → 승인 → 적용 → lint 순서입니다.
  4. --refresh-docs는 스킬 워크플로 플래그이며 런타임 installer 플래그가 아닙니다.
  5. 완료 훅과 wiki SessionEnd 캡처는 서로 별개이며 각각 명시적 승인이 필요합니다.
02

deep-interview

모호함과 사각지대를 확인된 요청으로
↗
설명 기반 매칭 가능 session only

명시된 모호함과 맥락상 가능한 사각지대를 함께 점검하되, 결과를 바꿀 중요한 지점만 한 번에 하나씩 질문해 확인된 요청으로 다시 씁니다.

언제
대상·범위·성공이 모호하거나 숨은 전제와 후속 영향을 점검해야 할 때
결과
현재 대화 안의 Clarified request와 사용자 확인
안 함
인터뷰 중 파일·스펙 작성, 기존 산출물 리뷰, 일반 모드의 자동 진행
Plugin invocation요청 문장과 함께
$ezpowers:deep-interview
인터뷰가 잘 끝나는 기준
  • 저장소에서 찾을 수 있는 사실은 먼저 조사하고 사용자에게 되묻지 않습니다.
  • 매 질문과 종료 판단 전에 사각지대를 내부 점검하고, 가능성과 영향이 모두 큰 후보만 꺼냅니다.
  • 매 턴 정확히 하나의 중요한 질문만 묻습니다.
  • 이미 충분히 결정된 요청에는 의례적인 사각지대 질문을 만들지 않습니다.
  • 요청을 다시 쓸 때 사용자 선호를 새로 발명할 필요가 없어야 합니다.
  • 마지막 요청은 사용자가 명시적으로 확인하거나 수정해야 완성됩니다.
  • 이미 Plan Mode라면 확인 뒤 같은 계획 대화를 이어가며, 확정된 의도는 다시 묻지 않습니다.
03

diagnose

재현부터 검증된 수정까지
↗
설명 기반 매칭 가능 evidence first

사용자의 정확한 증상을 명령으로 red 확인하고 최소화한 뒤에만 가설과 계측으로 첫 분기점을 찾습니다. 이후 회귀 신호·원인 수정· 원래 시나리오·관련 검사를 모두 green으로 만듭니다.

언제
버그, 실패한 테스트·빌드·통합, flaky 동작, 성능 회귀를 실제로 해결할 때
결과
baseline exact-red 영수증, red-before/green-after 증거, source-cause patch, 원증상 재실행
안 함
재현 전 가설·제품 수정, 인접 실패를 원증상으로 오인, assertion 약화, downstream 증상 은폐
Plugin invocation증상과 함께
$ezpowers:diagnose
진단과 수정의 경계
  • 명시 호출 또는 fix/debug 요청은 기본 FIX-COMPLETE이며 추가 수정 허가를 다시 묻지 않습니다.
  • analysis-only/no edits가 명시된 경우에만 읽기 전용 probe와 기존 테스트에서 멈춥니다.
  • exact-red 명령을 실제 실행하고 최소화하기 전에는 가설·root cause·제품 동작 변경이 금지됩니다.
  • 재현할 수 없으면 시도 결과와 필요한 access·capture·instrumentation을 요청하고 멈춥니다.
  • gate 이후 실제 인터페이스 seam의 회귀 테스트나 실행 가능한 최소 loop를 red로 고정합니다.
  • 세 번의 patch가 실패하면 종료하지 않고 exact-red loop를 다시 실행한 뒤 가설을 재구축합니다.
  • 관리 실행의 완료는 여전히 전체 verify와 certify가 판단합니다.
04

codebase-design

작은 인터페이스, 깊은 모듈
↗
설명 기반 매칭 가능 focused advisory

이름 붙이기 수준이 아니라 materially different한 인터페이스를 최소 두 개 비교해, 복잡성을 숨기고 변경·테스트를 한곳에 모으는 honest seam을 설계합니다.

언제
지정된 모듈·리팩터링의 책임, 의존성 방향, API, 테스트 표면을 정할 때
결과
대안 비교, 선택한 Module·Interface·Seam·Adapter·migration 경계
안 함
저장소 전체 스캔, 코드 구현, ADR·정식 아키텍처 문서의 자동 수정
Project invocation모듈을 지정
$codebase-design
깊이와 seam 판단법
  • 모듈 삭제 시 복잡성이 호출자로 퍼지면 깊이가 있고, 사라지면 pass-through일 수 있습니다.
  • 어댑터 하나는 가상 seam이며, 독립적으로 필요한 둘이 실제 변형을 증명합니다.
  • 호출자와 테스트는 같은 인터페이스 경계를 통과해야 합니다.
  • mock 편의만을 위해 추상화를 추가하지 않습니다.
05

improve-codebase-architecture

제품 코드 개선 후보 지도
↗
반드시 명시 호출 offline report

기존 제품 코드에서 얕은 모듈·새는 경계·흩어진 복잡성을 찾아 1–8개 후보와 before/after 도식을 안전한 임시 HTML 보고서로 렌더링합니다.

언제
특정 하위 시스템이나 최근 hotspot의 구조 개선 후보를 넓게 비교할 때
결과
OS 임시 경로의 오프라인 보고서, SHA-256 receipt, 선택 후보의 refactor brief
안 함
워크플로 하네스 감사, 저장소 파일 작성, 후보 자동 구현, CDN·원격 자산 사용
Project invocation범위를 명시
$improve-codebase-architecture
보고서 안전성과 다음 단계
  • 기존 저장소 상대 경로와 line-specific evidence가 있는 후보만 포함합니다.
  • renderer는 입력을 escape하고 repository 내부·기존 출력 파일을 거부합니다.
  • 보고서에는 script, 원격 요청, 이미지·폰트·분석 의존성이 없습니다.
  • 사용자가 후보 하나를 고른 뒤에만 codebase-design 방식으로 더 깊게 탐색합니다.
06

frontend-design

UI 결정을 구현 전에
↗
설명 기반 매칭 가능 advisory

화면 구조, 시각 방향, 상태, 토큰, 컴포넌트, 반응형·접근성 규칙, 그리고 실제로 확인할 시각 QA 오라클을 결정합니다.

언제
웹·모바일·데스크톱·TUI 표면의 외형이나 상호작용을 정해야 할 때
결과
docs/ux/frontend-design.md 디자인 계약
안 함
UI 코드 구현, 없는 Storybook/시각 diff 도구의 강제 도입
Plugin invocation구현 전에
$ezpowers:frontend-design
필수 결정 항목
  • 서로 다른 2–3개 방향과 구체적인 장단점, 선택 또는 위임 기록
  • 화면/경로 인벤토리, 로딩·빈 상태·오류·권한·성공 등의 상태 행렬
  • 토큰과 컴포넌트 정책, 반응형·입력 방식, 접근성 목표
  • 자산 출처, 시각 QA 증거, 규범적 목업이 있다면 신선도 규칙
07

design-architecture

기술 경계와 검증 설계
↗
명시 호출 before spec

합의된 제품 결정을 프로젝트의 경계, 소유권, 데이터 흐름, 수명주기, 배포·호환성, 실행 가능한 검증 설계로 고정합니다.

언제
기능 스펙을 쓰기 전에 구현이 기술 결정을 발명할 위험이 있을 때
결과
프로젝트별 아키텍처 산출물과 실제 엔트리포인트 검증 설계
안 함
코드 구현, 제품 요구 인터뷰, 모델·서브에이전트·재시도 정책 지정
Project invocationsetup 완료 후
$design-architecture
판단 기준과 연결점
  • 제품·도메인 선택이 열려 있으면 deep-interview로 돌아갑니다.
  • UI 방향은 frontend-design에 맡기고 산출물 경로와 오라클만 이어받습니다.
  • 사용자에게 보이는 주장은 실제 경계를 통과하는 프로젝트 로컬 검사로 증명합니다.
  • 필요한 어댑터가 없으면 주장을 약화하지 말고 선행 작업으로 기록합니다.
08

spec

합의된 결정을 수락 계약으로
↗
명시 호출 managed artifact

07 · Boundaries

누가 무엇을 책임하는지
분리해서 이해하세요

EZPowers는 코딩 에이전트가 아닙니다. 호스트가 구현하고, 프로젝트 로컬 런타임이 정해진 검사와 증거로 완료를 판정합니다.

EZPowers가 소유

  • 등록된 문서 그래프와 관리 spec/plan 데이터
  • 프로젝트별 exact argv 검사와 실제 stdout/stderr 증거
  • 증거·설정·워크스페이스 해시와 certification 신선도
  • resume 상태와 명시 승인된 chain의 frozen input·receipt·limits

Claude Code / Codex가 소유

  • 파일 편집과 셸 실행, 구현 순서의 실무 판단
  • 서브에이전트, worktree, sandbox, 권한과 일반 재시도
  • 호스트 네이티브 코드 리뷰와 실제 도구 사용
  • 로그인·비밀·결제·외부 시스템 등 호스트 경계
! 이 네 가지는 완료 증거가 아닙니다.

“테스트 이름이 있다”, “문자열이 존재한다”, “에이전트가 PASS라고 말했다”, “예전에 검사가 통과했다”는 주장만으로는 부족합니다. 실제 명령의 fresh all-scope PASS가 필요합니다.
모든 기능에 deep-interview부터 execute까지 전부 써야 하나요?

아닙니다. 모호하지 않으면 deep-interview를, UI가 아니면 frontend-design을, 기술 경계가 정해졌으면 design-architecture를 건너뜁니다. 이미 합의된 작은 작업은 spec → prepare-execute → execute가 일반적인 최소 경로입니다.

deep-interview가 끝나면 spec 파일을 자동으로 만들어 주나요?

아닙니다. 인터뷰는 현재 대화 안에서 확인된 요청만 만듭니다. 파일을 쓰거나 다음 스킬로 자동 handoff하지 않습니다. 다만 이미 Plan Mode라면 확인된 요청을 바탕으로 같은 호스트의 계획 수립을 계속하며, 필요하면 사용자가 spec을 별도로 호출합니다.

wiki에 적힌 내용을 곧바로 프로젝트 결정으로 써도 되나요?

안 됩니다. wiki는 로컬 보조 기억이며 canonical authority나 completion evidence가 아닙니다. 구현 전에 소스·문서·설정 등 저장소 근거로 재확인해야 합니다.

diagnose를 호출하면 버그도 바로 수정하나요?

네. 명시적으로 diagnose를 호출하거나 fix/debug를 요청하면 기본은 FIX-COMPLETE입니다. 단, exact-red와 최소화 전에는 가설이나 제품 수정을 하지 않습니다. 재현할 수 없으면 필요한 증거를 요청하고 멈춥니다. gate가 열리면 가설·root cause는 중간 진행이며 회귀 신호, 원인 수정, 원래 시나리오와 관련 검사까지 끝냅니다. “원인만”, “분석만”, “수정 금지”를 명시했을 때만 재현 가능한 경로에서도 코드 변경 전에 멈춥니다.

세 아키텍처 관련 스킬은 어떻게 다른가요?

codebase-design은 지정된 모듈의 인터페이스를 비교하는 집중 자문이고, improve-codebase-architecture는 명시적으로 기존 제품 코드를 넓게 스캔해 임시 보고서를 만듭니다. design-architecture만 프로젝트의 지속적인 경계·데이터 흐름·검증 설계 문서를 소유합니다.

harness-chain이 일반 execute보다 더 좋은 모드인가요?

우열 관계가 아닙니다. 일반 작업은 execute가 기본입니다. harness-chain은 사용자 부재 중에도 한 기능을 미리 승인한 한도까지 계속해야 하는 경우의 명시적 경로이며 구성·감사·승인 비용이 추가됩니다.

Claude Code와 Codex 결과가 완전히 동일한가요?

핵심 EZPowers 완료 판정은 같은 프로젝트 로컬 런타임을 사용합니다. 그러나 호출문, hook wire format, chain continuation 방식 같은 호스트 기능은 서로 다르며 동일하다고 가정하지 않습니다.

인증을 받은 뒤 파일 하나를 바꾸면 어떻게 되나요?

워크스페이스나 관리 입력이 바뀌면 이전 증거가 stale이 될 수 있습니다. 런타임 status를 다시 확인하고 필요한 전체 검증과 인증을 재실행해야 합니다.
